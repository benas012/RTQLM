# Buffered binary acquisition and server C processing

Implemented an opt-in `bufferedProcessing: "server"` device profile. The existing
`arm` default and decimation 1 remain available. No FPGA image or generator/optical
settings were changed by these experiments. The board reported v0.94 and a 1 Gb/s
Ethernet link.

## Implementation

The board reuses the SDK acquisition adapter, stops acquisition after both DMA
buffers fill, resolves each rail's own trigger pointer, and copies the wrapped
regions into owned RAM. It sends planar little-endian int16 ADC words. Server
processing reuses `nullifier.c` and the existing command/result implementation:
weighted projection, ADC offsets, voltage rejection tables when required,
calibration, formula ordering, rolling statistics, and result formatting. The
calibrated 1,024-sample waveform preview is retained. No averaging or downsampling
is performed for transmission.

DMA allocation requires a multiple of 64 samples. At decimation 2 the complete
312,512-sample/channel buffer is transferred (1,250,048 raw bytes), including 12
padding samples/channel. The processor uses the first 312,500 samples/channel:
exactly 5 ms at 62.5 MS/s. At decimation 1 it transfers 625,024/channel and processes
625,000/channel. The padding is not silently dropped on the board. Acquisition
duration including padding is 5.000192 ms at both rates.

The 308 ns fractional mode schedule is regenerated by the C configuration code:
19/20 samples at half rate, 38/39 at full rate. Configuration values expressed in
samples, including rail delay and end guards, still mean samples at the selected
rate; users must choose the corresponding sample count when preserving a physical
delay across rates. Existing calibration cannot be assumed valid at a new rate.

Control/launch uses existing SSH authentication. Bulk transfer can use SSH or a
single-client TCP listener on port 18903. TCP requires a fresh 256-bit bearer token
supplied through SSH; it closes the listener after accepting one connection. The
TCP data are unencrypted, intended for the trusted instrument LAN. Socket timeouts,
bounded lengths, capture sequence checks and session teardown handle interrupted
transfers. Reconnection requires calibration again. TCP_NODELAY and larger socket
buffers avoid the delays observed with the first TCP experiment.

Only one burst is in flight. Acquisition is stopped and the RAM buffer remains
owned until transmission completes. This prevents overwrite by the next capture;
it deliberately leaves acquisition gaps. A hardware lost-sample counter is not
available for this path, so hardware loss is reported as unknown, not zero.

## Measured results

Final run: 100 complete server bursts per case, local 1 ms E1 polling active, plus
30 ARM-only bursts per case. Both rails, 308 ns Gaussian-linear integration,
2,000-mode lab rolling variance, zero guards/delay, immediate trigger. Single mode
has one row per rail; cluster uses the existing four-term row. Three diagnostic
calibration captures and three identical-sample parity captures precede timing.
These diagnostic coefficients are not optical vacuum references.

| Rate | Calculation | Payload MB/s | Server bursts/s | ARM bursts/s | Complete median / p95 ms | Dead time median ms |
|---|---|---:|---:|---:|---:|---:|
| 62.5 MS/s | Single | 67.63 | 22.69 | 8.13 | 43.44 / 47.34 | 38.56 |
| 62.5 MS/s | Cluster | 67.35 | 21.83 | 10.51 | 43.77 / 56.23 | 38.94 |
| 125 MS/s | Single | 70.78 | 14.04 | 7.05 | 69.21 / 79.77 | 64.19 |
| 125 MS/s | Cluster | 77.33 | 15.38 | 8.70 | 64.42 / 66.98 | 59.45 |

The **62.5 MB/s target was exceeded for payload transfer** in both half-rate
cases. This is not sustained acquisition throughput across dead time: half-rate
wall-time payload throughput is about 27–28 MB/s, and only about 11% of wall time
contains acquired samples. Payload MB/s is total payload bytes divided by summed
payload receive times, after reading each small metadata header. Complete bursts/s
includes capture, transfer, server C execution, JSON output, local IPC and decoding.
Measurements use decimal MB. The server executable ran as x86-64 Linux under WSL;
the orchestration/application ran on Windows.

Half-rate median stages: acquisition plus RAM copy 12.86–13.12 ms, of which copy
6.16–6.42 ms; payload receive 16.75–16.96 ms; C projection 0.62–0.81 ms; calculation
and result construction 1.85–2.36 ms. The other complete-burst time includes command
transport, scheduling, serialization, local process I/O and JSON decoding. Stage
medians must not be summed as if they were a measured individual burst.

All 400 timed server bursts completed. Sequence checks found no missing captures;
truncated payloads would abort the session. No buffer overwrite is permitted by
the serial ownership design; this is not evidence of gap-free ADC acquisition.
The first SSH run measured only 11–12 MB/s. Preliminary TCP results varied, including
one half-rate run at 61.7 MB/s; the target is measured run-level throughput, not a
per-burst or hard real-time guarantee.

The application adapter also completed 50 live captures with the existing
`lab_gaussian_linear_cosine` shape, lab rolling statistics, diagnostic calibration,
calibrated previews and normal result conversion while remote pin polling ran:
19.32 bursts/s, no failures. This differs from the controlled benchmark configuration.

## Numerical and measurement agreement

ARM and x86 processed identical physical buffers and identical calibration buffers
in independent C processor states. Every returned quadrature, formula value,
variance, dB value and variance count was compared at full result resolution.
Maximum absolute discrepancy in the final comparison was 1.11e-16. This checks
platform parity; shared C implementation errors are additionally covered by the
existing independent weighted, timing, raw projection and statistics tests.

**Half rate is not established as scientifically interchangeable with full rate.**
Saved sequential hardware captures gave half/full integrated variance ratios
0.543–0.566. Taking every other sample of the same full-rate recording instead
gave ratios 2.215–2.287, correlations 0.611–0.623 and relative RMS differences
1.170–1.200. This thinning test is not a model of the FPGA decimator's filtering.
The sequential hardware comparison includes drift and uses one retained diagnostic
capture per case. Neither comparison isolates optical variance or establishes
squeezing agreement. Optical settings were held untouched; a scientifically valid
cross-rate comparison requires appropriate per-rate optical references and a
controlled signal/noise comparison. Do not reuse the full-rate vacuum calibration.

## E1 physical pin 3

The official STEMlab 125-14 pinout maps **E1 physical pin 3 to DIO0_P / EXT TRIG,
FPGA G17**, a 3.3 V digital input. It reports HIGH/LOW, not measured voltage.
DIO3_P is physical pin 9; older DIO3_P gate measurements are a different pin.
See the [official pinout](https://redpitaya.readthedocs.io/en/latest/developerGuide/hardware/ORIG_GEN/125-14/top.html)
and [digital I/O API](https://redpitaya.readthedocs.io/en/latest/appsFeatures/remoteControl/command_list/commands-digital.html).

The isolated poller sets DIO0_P to input and restores the prior direction. It uses
absolute monotonic deadlines, skips missed deadlines rather than catching up, and
records board timestamps, read duration, digital state and status in RAM. Results
are sent to the server after polling. It runs in a separate board process, so
sampling continues while acquisition or network transmission blocks the worker.

| Active benchmark | Interval median ms | p95 ms | p99 ms | Maximum ms |
|---|---:|---:|---:|---:|
| Half single | 1.000 | 1.267 | 1.553 | 3.927 |
| Half cluster | 1.000 | 1.356 | 1.702 | 4.066 |
| Full single | 1.000 | 1.312 | 1.520 | 6.348 |
| Full cluster | 0.999 | 1.408 | 1.631 | 4.401 |

Each poller collected 10,000 samples with zero reported read errors. These interval
statistics select the active server acquisition/transfer period; raw timestamps
and levels are retained in the evidence. Software polling can miss transitions
between reads; no 1 ms hard deadline guarantee is claimed.

Remote request/response polling during the application smoke test had 1.220 ms
median interval, 1.866 ms p95, 3.495 ms maximum and 1.002 ms median round trip. Local
timestamped polling is preferable. Comparing separate TCP runs with and without
local polling shows overlapping throughput variation, not a controlled causal
impact estimate. A follow-up run of the final build with polling disabled measured
20.87 bursts/s single and 25.96 cluster (62.73 and 75.36 MB/s), versus 22.69 and
21.83 with polling enabled. The apparent effects have opposite signs: about +8.8%
single and -15.9% cluster. These sequential runs are affected by host/network
variation and do not support a single causal overhead estimate. Polling was
demonstrated concurrently without failed captures; a randomized repeated trial
would be needed to isolate its performance cost.

## Use and reproduce

Build `make buffered` on the server and `make buffered-board` on the board. Keep
the ARM targets installed. Configure `QL_BUFFERED_BOARD_EXECUTABLE` with the board
worker path and `QL_BUFFERED_SERVER_COMMAND` with a JSON command array for the local
worker. `QL_BUFFERED_TRANSPORT` selects `tcp` (default) or `ssh`;
`QL_BUFFERED_BINARY_PORT` defaults to 18903. The validated isolated board executable
is `/root/rtqlm-buffered-server-20261101/build/rp-buffered-board`.

Use a device profile with `acquisitionMode: "buffered"`,
`bufferedProcessing: "server"`, both channels enabled, `decimation: 2`,
`captureSamples: 312512`. For full rate use decimation 1 and 625024 samples.
To select the old path use `bufferedProcessing: "arm"`. Selection is exposed in the
device API/profile; no dedicated receiver dropdown was added. Existing saved
profiles remain on ARM. FPGA loading is deliberately not part of the server path.

Reproduction scripts are in `native/redpitaya_nullifiers/tests`:

```
benchmark_buffered_server.py --prepare --iterations 100 --tcp --poll --output ../benchmarks/results/buffered-server-validation.json
check_server_live.py
assess_buffered_rates.py
```

`--prepare` uploads an isolated build and does not replace the active deployment.
The scripts require exclusive ADC ownership and existing v0.94 firmware. The
recorded rate-assessment inputs live under `tmp/buffered-recordings`; they are not
committed as multi-megabyte fixtures. Evidence summaries are in
`../benchmarks/results/buffered-server-validation.json`,
`buffered-rate-agreement.json`, and `buffered-application-smoke.json`.

Validation: 51 focused Python application/profile/receiver tests passed; 3 actual
binary-worker tests passed (padding exclusion, truncation, oversized counts);
27 native command tests, 8 stream tests and 28 SDK acquisition tests passed.
Independent C numerical suites also passed, including 5,600 weighted CPU/DMA
scenarios, more than 8.7 million weighted comparisons and one million temporal
boundary checks. The final board check still reported v0.94 and no remaining
isolated acquisition or polling process.
